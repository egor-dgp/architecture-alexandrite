# Выбор и настройка мониторинга в системе "Александрит"

## Мотивация

### Текущая ситуация и проблемы

Компания "Александрит" столкнулась с критическими проблемами в отслеживании заказов, которые напрямую связаны с отсутствием полноценной системы мониторинга:

1. **Невидимость в процессах обработки заказов**: Клиенты жалуются на неполученные заказы и просроченные сроки, но команда не может быстро определить, на каком этапе происходит сбой. Является ли это проблемой онлайн-магазина, CRM, MES или интеграции через RabbitMQ?

2. **Проблемы с API интеграцией**: После открытия API для внешних партнёров нагрузка выросла линейно (+100 заказов в месяц), но система начала отказывать. Представители компаний через API также не получают свои заказы, но у нас нет метрик для понимания причины.

3. **Деградация пользовательского опыта операторов**: Дашборд MES долго загружается, что влияет на способность операторов взять заказ в работу. Без мониторинга невозможно определить, является ли это проблемой БД, бэкенда или избыточного количества данных.

4. **Потеря контрактов**: Компания уже потеряла несколько крупных контрактов из-за проблем с обработкой заказов. Дальнейшие потери неизбежны без видимости в систему.

5. **Ограниченность текущих данных**: Яндекс Метрика собирает только клиентскую информацию (B2C сегмент). Данные не покрывают:
    - Интеграцию через API (B2B сегмент)
    - Внутренние процессы CRM и MES
    - Поведение RabbitMQ очереди
    - Производительность расчёта стоимости в MES (2-30 минут)

### Ценность добавления мониторинга

**Для бизнеса:**
- Быстрое выявление и устранение проблем с заказами, снижение количества жалоб
- Возможность удержать существующие контракты и предотвратить потерю новых
- Данные для понимания влияния нагрузки на выполнение SLA (3 недели на заказ)
- Видимость в B2B API интеграцию и возможность гарантировать качество обслуживания

**Для техники:**
- Быстрая идентификация узких мест при увеличении нагрузки
- Ранее предупреждение о деградации производительности до жалоб пользователей
- Возможность прогнозировать потребность в масштабировании
- Данные для принятия архитектурных решений (например, кеширование дашборда MES)

**Для DevOps и SRE:**
- Контроль доступности сервисов в трёх окружениях (dev, release, prod)
- Быстрое выявление проблем после деплоя
- Возможность автоматизировать обнаружение и оповещение об ошибках
- Сокращение времени на отладку проблем

## Выбор подхода к мониторингу

Для системы "Александрит" рекомендуется использовать **комбинированный подход**, в котором различные части системы мониторятся разными методами в зависимости от их функции:

### 1. RED (Rate, Errors, Duration) для HTTP-сервисов и API

**Применяется к:**
- Онлайн-магазин (Vue + Spring Boot)
- CRM (Vue + Spring Boot)
- MES (React + C#)
- Public API для интеграции

**Обоснование:** RED метод специально предназначен для контроля сервисов, управляемых запросами. Это идеально подходит для нашего случая, где:
- Нужно отслеживать пропускную способность API (Rate)
- Критично отслеживать ошибки при обработке заказов (Errors)
- Необходимо контролировать время ответа, особенно для расчёта стоимости (Duration)

### 2. USE (Utilization, Saturation, Errors) для инфраструктуры

**Применяется к:**
- EC2 инстансы (основные приложения)
- Управляемые базы данных Yandex Cloud
- RabbitMQ
- Диск и память

**Обоснование:** USE метод предназначен для анализа ресурсов, и наша инфраструктура состоит именно из ресурсов. Это поможет понять:
- Утилизация: насколько активно используются ресурсы
- Насыщенность: начинает ли накапливаться очередь работы
- Ошибки: возникают ли проблемы с ресурсами

### 3. Четыре золотых сигнала (Latency, Traffic, Errors, Saturation) для интеграции

**Применяется к:**
- RabbitMQ (сообщения между CRM и MES)
- Связь между сервисами

**Обоснование:** Этот подход показывает здоровье системы в целом и помогает быстро ответить на вопрос "Что происходит с нашей интеграцией?"

## Описание метрик и их назначение

### А. HTTP-сервисы (RED метод)

#### A1. Rate (Частота запросов)

**Метрика: `http_requests_total`**
- **Зачем нужна:** Понять пропускную способность сервиса, отследить рост нагрузки
- **Ярлыки:**
    - `service` (значения: "online-shop", "crm", "mes", "public-api")
    - `method` (значения: "GET", "POST", "PUT", "DELETE", "PATCH")
    - `endpoint` (примеры: "/orders", "/products", "/calculate-price", "/status")
    - `environment` (значения: "dev", "release", "prod")

**Дополнительная метрика: `http_requests_per_second_current`**
- Текущее значение RPS для быстрого мониторинга пиковых нагрузок
- **Ярлыки:** service, environment

#### A2. Errors (Количество ошибок)

**Метрика: `http_requests_failed_total`**
- **Зачем нужна:** Отследить проблемы при обработке заказов, которые привели к потере контрактов
- **Ярлыки:**
    - `service`
    - `http_status` (примеры: "400", "404", "500", "503", "timeout")
    - `endpoint`
    - `environment`

**Метрика: `http_request_errors_by_reason`**
- Детализация причин ошибок (помогает различить ошибки валидации от ошибок сервера)
- **Ярлыки:**
    - `service`
    - `error_type` (значения: "validation_error", "business_logic_error", "database_error", "external_service_error", "timeout")
    - `environment`

#### A3. Duration (Длительность запроса)

**Метрика: `http_request_duration_seconds` (гистограмма)**
- **Зачем нужна:** Отследить, почему дашборд MES долго загружается, и контролировать время расчёта стоимости (2-30 минут)
- **Ярлыки:**
    - `service`
    - `method`
    - `endpoint`
    - `environment`
- **Квантили для отслеживания:**
    - p50 (медиана) — нормальная ситуация
    - p95 — когда начинается деградация
    - p99 — экстремальные случаи
    - p99.9 — outliers, которые могут привести к таймаутам

**Специальная метрика: `mes_price_calculation_duration_seconds` (гистограмма)**
- Отдельное отслеживание времени расчёта стоимости, так как это критичный процесс
- **Ярлыки:**
    - `polygon_complexity` (значения: "low", "medium", "high", "extreme") — сложность 3D модели
    - `source` (значения: "online-shop-upload", "online-shop-constructor", "public-api")
    - `environment`

### B. Интеграция и очереди (RED метод + четыре золотых сигнала)

#### B1. RabbitMQ метрики

**Метрика: `rabbitmq_queue_messages_total`**
- **Зачем нужна:** Отследить, не накапливаются ли сообщения в очереди между CRM и MES
- **Ярлыки:**
    - `queue_name` (примеры: "crm-to-mes-orders", "mes-to-crm-status-updates")
    - `environment`

**Метрика: `rabbitmq_queue_messages_ready`**
- **Зачем нужна:** Текущее количество необработанных сообщений (насыщенность)
- **Ярлыки:** queue_name, environment

**Метрика: `rabbitmq_messages_processed_total`**
- **Зачем нужна:** Скорость обработки сообщений
- **Ярлыки:**
    - `queue_name`
    - `status` (значения: "success", "failed", "timeout")
    - `environment`

**Метрика: `rabbitmq_message_processing_duration_seconds`**
- **Зачем нужна:** Время обработки сообщения (duration в RED)
- **Ярлыки:** queue_name, environment

**Метрика: `rabbitmq_queue_consumer_count`**
- **Зачем нужна:** Количество потребителей очереди — если потребителей ноль, очередь никто не обрабатывает
- **Ярлыки:** queue_name, environment

#### B2. API интеграция (PUBLIC API)

**Метрика: `public_api_client_requests_total`**
- **Зачем нужна:** Отследить нагрузку от каждого клиента B2B
- **Ярлыки:**
    - `client_id` (идентификатор партнёра)
    - `endpoint` (примеры: "/calculate-price", "/create-order", "/get-status")
    - `environment`

**Метрика: `public_api_client_errors_total`**
- **Зачем нужна:** Отследить, не отказываем ли мы конкретному клиенту
- **Ярлыки:**
    - `client_id`
    - `error_type` (значения: "rate_limit_exceeded", "quota_exceeded", "invalid_request", "server_error")
    - `environment`

### C. Инфраструктура (USE метод)

#### C1. EC2 инстансы

**Метрика: `node_cpu_usage_percent`**
- **Зачем нужна:** Утилизация процессора
- **Ярлыки:**
    - `instance_name` (примеры: "online-shop-prod", "crm-prod", "mes-prod")
    - `environment`
    - `instance_type`

**Метрика: `node_memory_usage_percent`**
- **Зачем нужна:** Утилизация памяти
- **Ярлыки:** instance_name, environment

**Метрика: `node_disk_usage_percent`**
- **Зачем нужна:** Утилизация диска
- **Ярлыки:**
    - instance_name
    - environment
    - mount_point (примеры: "/", "/var/log")

**Метрика: `node_network_io_errors_total`**
- **Зачем нужна:** Ошибки сетевого ввода-вывода
- **Ярлыки:** instance_name, interface (примеры: "eth0", "eth1")

#### C2. Управляемые базы данных

**Метрика: `db_connection_pool_active`**
- **Зачем нужна:** Текущее количество активных соединений (утилизация)
- **Ярлыки:**
    - `database_name` (примеры: "online-shop-db", "crm-db", "mes-db")
    - `environment`

**Метрика: `db_connection_pool_waiting`**
- **Зачем нужна:** Количество запросов в очереди на соединение (насыщенность)
- **Ярлыки:** database_name, environment

**Метрика: `db_query_duration_seconds` (гистограмма)**
- **Зачем нужна:** Время выполнения запросов
- **Ярлыки:**
    - `database_name`
    - `query_type` (примеры: "SELECT", "INSERT", "UPDATE", "DELETE")
    - `table_name`
    - `environment`

**Метрика: `db_slow_queries_total`**
- **Зачем нужна:** Счётчик медленных запросов (порог, например, > 1 секунда)
- **Ярлыки:**
    - `database_name`
    - `query_type`
    - `table_name`
    - `environment`

**Метрика: `db_replication_lag_seconds`**
- **Зачем нужна:** Задержка репликации (если настроена репликация для высокой доступности)
- **Ярлыки:** database_name, environment

#### C3. Диск и хранилище

**Метрика: `disk_io_read_bytes_total`**
- **Зачем нужна:** Объём прочитанных данных
- **Ярлыки:** instance_name, device, environment

**Метрика: `disk_io_write_bytes_total`**
- **Зачем нужна:** Объём записанных данных
- **Ярлыки:** instance_name, device, environment

### D. Бизнес-метрики

#### D1. Обработка заказов

**Метрика: `orders_created_total`**
- **Зачем нужна:** Отследить количество новых заказов в день
- **Ярлыки:**
    - `source` (значения: "online-shop", "public-api")
    - `environment`

**Метрика: `orders_by_status`**
- **Зачем нужна:** Распределение заказов по статусам — помогает выявить накопление заказов на определённом этапе
- **Ярлыки:**
    - `status` (значения: "INITIATED", "FILE_UPLOADED", "SUBMITTED", "PRICE_CALCULATED", "MANUFACTURING_APPROVED", "MANUFACTURING_STARTED", "MANUFACTURING_COMPLETED", "PACKAGING", "SHIPPED", "CLOSED")
    - `source` (значения: "online-shop", "public-api")
    - `environment`

**Метрика: `orders_processing_time_days` (гистограмма)**
- **Зачем нужна:** Отследить, соблюдаются ли SLA (3 недели на заказ)
- **Ярлыки:**
    - `source`
    - `status_transition` (примеры: "SUBMITTED_to_PRICE_CALCULATED", "PRICE_CALCULATED_to_MANUFACTURING_APPROVED", "MANUFACTURING_STARTED_to_COMPLETED")
    - `environment`

**Метрика: `orders_overdue_total`**
- **Зачем нужна:** Счётчик просроченных заказов — основной индикатор проблем с бизнесом
- **Ярлыки:**
    - `source`
    - `days_overdue_bucket` (значения: "1-7", "7-14", "14-30", "30+")
    - `environment`

#### D2. Расчёты стоимости

**Метрика: `price_calculations_total`**
- **Зачем нужна:** Количество запросов на расчёт стоимости
- **Ярлыки:**
    - `source`
    - `status` (значения: "success", "failed", "timeout")
    - `environment`

**Метрика: `price_calculation_errors_total`**
- **Зачем нужна:** Отследить ошибки в расчётах стоимости
- **Ярлыки:**
    - `error_type` (примеры: "invalid_model", "model_too_complex", "service_unavailable")
    - `source`
    - `environment`

### E. Логирование (дополнение к метрикам)

Хотя мониторинг метрик — основной фокус, для полной картины необходимо централизованное логирование.

**Что логировать:**
- Ошибки и исключения во всех приложениях
- Переходы между статусами заказов
- Сообщения в RabbitMQ (начало, конец, ошибки обработки)
- Запросы к внешним API
- Slow queries в БД (> 1 сек)
- Запуски и остановки сервисов

**Инструмент:** ELK стек (Elasticsearch, Logstash, Kibana) или аналог
