# Архитектурное решение по трейсингу - Александрит

## Анализ точек отказа в системе

### Критические пути заказа, где возможны сбои

На основе анализа C4-диаграммы и описания процесса обработки заказов идентифицированы следующие системы и связи, требующие покрытия трейсингом:

#### 1. Онлайн-магазин → CRM (HTTP Request)
- **Где может сломаться:** Заказ создается в онлайн-магазине, но CRM его не получает или получает с ошибкой
- **Признаки:** Заказ в статусе SUBMITTED, но в CRM его нет
- **Риск:** Высокий - прямой контакт с клиентом (B2C)

#### 2. CRM → RabbitMQ → MES (Асинхронная интеграция)
- **Где может сломаться:**
    - Сообщение не попало в очередь
    - Сообщение в очереди, но MES его не обработал
    - Сообщение обработано, но статус не вернулся в CRM
- **Признаки:** Заказ зависает на статусе MANUFACTURING_APPROVED, операторы не видят его в MES
- **Риск:** Высокий - основной путь обработки заказов

#### 3. Public API → MES → CRM (B2B интеграция)
- **Где может сломаться:**
    - API получил запрос, но не отправил его в MES
    - MES обработал, но статус не вернулся через API
    - Timeout при расчёте стоимости (2-30 минут)
- **Признаки:** Партнёры не получают статус заказа, но заказ реально создан
- **Риск:** Критический - потеря контрактов

#### 4. MES → Расчёт стоимости (внутренний процесс)
- **Где может сломаться:**
    - 3D-модель слишком сложная (30 минут обработки)
    - Таймаут в процессе расчёта
    - Ошибка валидации модели
- **Признаки:** Заказ зависает в статусе FILE_UPLOADED или SUBMITTED
- **Риск:** Высокий - прямое влияние на UX пользователя

#### 5. MES → RabbitMQ → CRM (Обратная связь)
- **Где может сломаться:**
    - MES обновил статус, но сообщение потеряется в очереди
    - CRM сообщение получил, но не обновил заказ
- **Признаки:** Статус заказа не обновляется в CRM, хотя в MES уже готово
- **Риск:** Высокий - клиент видит неправильный статус

#### 6. Дашборд MES (прямой запрос к БД)
- **Где может сломаться:**
    - Слишком много открытых заказов в памяти
    - Connection pool переполнен
    - Медленные SQL запросы
- **Признаки:** Оператор не может открыть список заказов, не может взять новый
- **Риск:** Высокий - прямое влияние на скорость заработка операторов

## Данные для трейсинга

### Обязательные элементы каждого спана (span)

Для каждого спана (единицы работы в трейсе) должны быть собраны:

1. **Идентификаторы:**
    - `trace_id` - уникальный идентификатор всей цепочки (один заказ = один trace_id)
    - `span_id` - идентификатор конкретного спана
    - `parent_span_id` - идентификатор родительского спана
    - `order_id` - бизнес-идентификатор заказа

2. **Контекст:**
    - `service_name` - имя сервиса (online-shop, crm, mes, public-api)
    - `environment` - окружение (dev, release, prod)
    - `operation` - название операции (create-order, calculate-price, update-status)
    - `timestamp` - время события (с миллисекундной точностью)
    - `duration_ms` - длительность спана в миллисекундах

3. **Источник запроса:**
    - `source` - откуда пришёл запрос (online-shop, public-api, internal-system)
    - `user_id` (если применимо) - для B2C заказов
    - `client_id` (если применимо) - для B2B заказов через API
    - `ip_address` - IP клиента

4. **Статус выполнения:**
    - `status` - успех/ошибка (success, error, timeout)
    - `error_type` - тип ошибки (if status == error)
    - `error_message` - сообщение ошибки
    - `http_status_code` - HTTP код ответа
    - `exception_stacktrace` - стек вызовов при ошибке

5. **Специфичные для бизнеса:**
    - `order_status` - текущий статус заказа (INITIATED, SUBMITTED, PRICE_CALCULATED и т.д.)
    - `order_previous_status` - предыдущий статус (для отслеживания переходов)
    - `model_complexity` - сложность 3D модели для расчёта (low, medium, high, extreme)
    - `estimated_processing_time_minutes` - для прогноза времени обработки

6. **Системные метрики:**
    - `db_query_time_ms` - время выполнения DB запроса
    - `queue_message_size_bytes` - размер сообщения в очереди
    - `queue_processing_time_ms` - время обработки сообщения в очереди
    - `request_payload_size_bytes` - размер входного запроса
    - `response_payload_size_bytes` - размер выходного ответа

7. **Логические связи:**
    - `message_queue_id` - идентификатор сообщения в очереди (для RabbitMQ)
    - `parent_order_id` - если заказ создан из другого заказа (редкое, но возможно)

## Мотивация

### Текущие проблемы, решаемые трейсингом

1. **Невидимость в асинхронных процессах**: Когда заказ зависает между CRM и MES через RabbitMQ, команда не знает, где именно произошёл сбой:
    - Сообщение не попало в очередь?
    - MES не обработал сообщение?
    - MES обработал, но статус не вернулся?

   **Трейсинг показывает:** Точно, на каком шаге потеряется каждое сообщение.

2. **Недостаточность логов**: Логи разброса по разным приложениям (онлайн-магазин на Java, MES на C#, интеграция через RabbitMQ). Даже с централизованным логированием (ELK) сложно собрать полную картину одного заказа.

   **Трейсинг показывает:** Полная цепочка событий одного заказа в одном месте.

3. **Сложность отладки API интеграции**: Партнёры жалуются, что не получили статус заказа, но команда не может быстро понять, потеряется ли запрос на стороне партнёра или на нашей.

   **Трейсинг показывает:** Точный момент, когда запрос пришёл и когда ответ отправлен.

4. **Проблемы с дашбордом MES**: Оператор жалуется, что дашборд долго загружается. Это БД медленно отвечает? Бэкенд зависает? Frontend долго рендерит?

   **Трейсинг показывает:** Время в каждом слое (frontend → backend → db и обратно).

5. **Потеря SLA из-за timeout**: Расчёт стоимости занимает 2-30 минут в зависимости от сложности модели. Как мы знаем, когда нужно отправить уведомление клиенту, что это займёт долго?

   **Трейсинг показывает:** Распределение времени между компонентами внутри MES.

### Метрики, на которые повлияет трейсинг

#### Технические метрики:

1. **MTTR (Mean Time To Repair)** - среднее время восстановления после сбоя
    - **До:** 30-60 минут (нужно перелопачивать логи в разных сервисах)
    - **После:** 5-10 минут (видимость в один клик через trace)
    - **Улучшение:** 6x-10x

2. **Error detection latency** - время от возникновения ошибки до её обнаружения
    - **До:** От нескольких минут (если оператор вручную проверит) до часов (если клиент пожалуется)
    - **После:** < 1 минута (автоматическое обнаружение через monitoring traces)
    - **Улучшение:** 60x+

3. **P99 latency при обработке заказов**
    - **До:** Unknown (нет полной видимости)
    - **После:** Будет известно точно, где происходит задержка
    - **Ожидание:** Выявить узкие места и оптимизировать

#### Бизнес-метрики:

1. **Количество просроченных заказов**
    - **До:** +100 заказов просроченных ежемесячно
    - **После:** -70% за счёт быстрого обнаружения и устранения проблем
    - **Бизнес-ценность:** ~$50K в месяц от удержания контрактов

2. **Количество жалоб от клиентов B2B через API**
    - **До:** Ежедневные жалобы, потеря контрактов
    - **После:** -80% жалоб за счёт быстрого восстановления и SLA гарантий
    - **Бизнес-ценность:** Удержание $200K+ в контрактах

3. **Удовлетворённость операторов**
    - **До:** Операторы не могут понять, почему заказ не видно, теряют заработок
    - **После:** Видимость в систему → справедливое распределение заказов → рост удовлетворённости
    - **Бизнес-ценность:** Снижение текучести кадров, стабильная производительность

## Предлагаемое решение

### Архитектура трейсинга

Рекомендуется внедрить распределённое трейсирование с использованием **OpenTelemetry** и **Jaeger** как хранилища и визуализации.

#### Почему OpenTelemetry + Jaeger?

1. **Стандартизация**: OpenTelemetry - CNCF стандарт для наблюдаемости, поддерживается всеми основными языками (Java, C#, Node.js и т.д.)
2. **Бесплатно и open-source**: Jaeger полностью бесплатен, можно развернуть на собственной инфраструктуре
3. **Context propagation**: Автоматическое распространение контекста трейса через HTTP, gRPC, RabbitMQ
4. **Инструментация библиотек**: Spring Boot, RabbitMQ, Elasticsearch и другие уже имеют встроенную поддержку
5. **Фильтрация и sampling**: Можно отправлять трейсы только для ошибок (head-based sampling) или статистически (tail-based sampling)

### Компоненты архитектуры

#### Новые компоненты (красные на диаграмме):

1. **OpenTelemetry SDK** - встраивается в каждое приложение
    - Онлайн-магазин: Spring Boot OpenTelemetry starter
    - CRM: Spring Boot OpenTelemetry starter
    - MES: OpenTelemetry .NET SDK
    - Public API: Spring Boot OpenTelemetry starter

2. **OTLP Exporter** - экспортер, встроенный в каждое приложение
    - Отправляет трейсы по протоколу OTLP (OpenTelemetry Protocol) на Jaeger Collector
    - Батчинг: отправляет несколько спанов вместе для эффективности
    - Retry логика для надёжности

3. **Jaeger Collector** - промежуточный сервис для сбора трейсов
    - Получает трейсы от всех приложений (OTLP, Jaeger, Zipkin протоколы)
    - Фильтрует и обогащает данные (добавляет метаданные окружения)
    - Отправляет в storage backend

4. **Jaeger Storage Backend** - хранилище трейсов
    - Elasticsearch (рекомендуется для масштабируемости)
    - Альтернатива: Cassandra или память приложения (только для dev)

5. **Jaeger UI** - веб-интерфейс для просмотра трейсов
    - Поиск по order_id, trace_id, service, operation
    - Визуализация полного пути заказа
    - Анализ latency bottlenecks

#### Инструментация компонентов:

1. **Онлайн-магазин (Java Spring Boot)**
   ```
   - Добавить зависимость: spring-boot-starter-actuator + spring-boot-starter-otel
   - Инструментировать:
     * Controller layer - HTTP запросы к CRM
     * Service layer - создание заказа, валидация
     * Database layer - операции с БД
   ```

2. **CRM (Java Spring Boot)**
   ```
   - Добавить зависимость: spring-boot-starter-actuator + spring-boot-starter-otel
   - Инструментировать:
     * RabbitMQ producer/consumer - отправка/получение сообщений
     * Controller layer - API к онлайн-магазину и Public API
     * Service layer - бизнес-логика одобрения заказа
     * Database layer - сохранение статуса заказа
   ```

3. **MES (C# ASP.NET Core)**
   ```
   - Добавить NuGet пакеты: OpenTelemetry.Exporter.Otlp, OpenTelemetry.Instrumentation.AspNetCore
   - Инструментировать:
     * RabbitMQ consumer - получение заказов из CRM
     * Расчёт стоимости - измерение времени обработки 3D модели
     * Database layer - запросы к МЕС БД
     * API response к Public API
   ```

4. **Public API (Java Spring Boot)**
   ```
   - Добавить зависимость: spring-boot-starter-actuator + spring-boot-starter-otel
   - Инструментировать:
     * HTTP запросы от клиентов B2B (с client_id как ярлык)
     * Вызовы к MES для расчёта стоимости
     * Синхронизация статуса с CRM через RabbitMQ
   ```

5. **RabbitMQ**
   ```
   - Встроенная поддержка context propagation через message headers
   - Ярлыки: queue_name, message_size, processing_time
   ```

## Компромиссы

### Случаи, где трейсинг менее полезен или более дорог

1. **Offline сценарии**
    - **Проблема:** Если клиент создаёт заказ в мобильном приложении без интернета, трейсинг не будет работать до синхронизации
    - **Решение:** Использовать локальное логирование на mobile app, затем соединить в цепь после синхронизации
    - **Стоимость:** Дополнительная разработка логики на мобильном клиенте

2. **Проприетарная система MES**
    - **Проблема:** MES был куплен с исходным кодом, но это legacy код на C#. Может быть сложным добавить инструментацию OpenTelemetry
    - **Решение:**
        * Вариант A: Использовать proxy/sidecar pattern (например, Envoy) для перехвата трейсов без изменения кода MES
        * Вариант B: Внедрить обёртку вокруг критичных функций (calculate-price) с явным логированием в OpenTelemetry
    - **Стоимость:** 3-5 дней разработки на C#

3. **Громадный объём трейсов в prod**
    - **Проблема:** Если трассировать все 100% заказов, это может быть 100K трейсов в день, требующих места в Elasticsearch
    - **Решение:** Использовать sampling:
        * Head-based: Отправлять 100% трейсов с ошибками, 10% успешных
        * Tail-based: Отправлять все трейсы, но Jaeger Collector отсеивает 90% успешных до сохранения
    - **Рекомендация:** Начать с 50% sampling, потом оптимизировать на основе данных
    - **Стоимость:** Storage будет ~500GB в месяц при 50% sampling (vs 1TB при 100%)

4. **Latency добавление из-за отправки трейсов**
    - **Проблема:** Каждый спан нужно собрать и отправить на Jaeger Collector. Это может добавить 5-10ms к каждому запросу
    - **Решение:**
        * Использовать асинхронный export (batch processing)
        * Jaeger SDK по умолчанию буферизирует спаны и отправляет батчами
    - **Рекомендация:** Батч size = 100 спанов, отправка каждые 5 сек или при переполнении
    - **Ожидаемый оверхед:** < 1ms на запрос (незаметно для пользователя)

5. **Чувствительные данные в трейсах**
    - **Проблема:** Трейсы содержат payload заказа, включая адреса клиентов, детали платежей
    - **Решение:** Использовать span processors для маскирования/удаления чувствительных данных
    - **Пример правила:**
      ```json
      {
        "attribute_processor": {
          "exclude_keys": ["credit_card", "ssn", "password"],
          "redact_pattern": "phone_number: \\d{10,}"
        }
      }
      ```
    - **Стоимость:** Настройка в конфиге, no code needed

6. **Трейсинг через third-party API (например, логистические партнёры)**
    - **Проблема:** Мы не контролируем логистические партнёры, они не будут отправлять нам трейсы
    - **Решение:**
        * Трейсировать наши вызовы к их API
        * Попросить партнёров отправлять нам ID correlation (x-correlation-id header)
        * Логировать на нашей стороне timing вызовов
    - **Ограничение:** Не будет видно, что происходит внутри их систем
    - **Приемлемо:** Потому что это не в нашем control

## Безопасность

### Внутренние меры безопасности (для сотрудников "Александрита")

1. **Аутентификация и авторизация в Jaeger UI**
    - **Реализация:** Jaeger UI поместить за reverse proxy (nginx) с OAuth2 аутентификацией через корпоративный OIDC провайдер (или собственный)
    - **Правило доступа:**
        * Роль "Engineering" - полный доступ к трейсам всех сервисов
        * Роль "Support" - доступ только к трейсам заказов (фильтр по order_id), видны все поля
        * Роль "DevOps" - полный доступ + управление Jaeger конфигурацией
        * Роль "Product" - доступ к трейсам с фильтром (только p50, p95 latencies, без payload)
    - **Логирование доступа:** Все попытки доступа логируются в centralized audit log

2. **Сетевая безопасность**
    - **Jaeger Collector работает внутри VPC**, не доступен из интернета
    - **OTLP Exporter → Jaeger Collector:** Используется TLS (mutual TLS если между разными окружениями)
    - **Elasticsearch:** Не доступна напрямую, только через Jaeger API
    - **Файрвол:** Открыты только необходимые порты (6831/UDP for Jaeger Agent, 14250/gRPC for OTLP)

3. **Data retention и удаление**
    - **Политика хранения:** Трейсы хранятся 7 дней в dev, 30 дней в prod
    - **Automatic cleanup:** Elasticsearch автоматически удаляет старые индексы через curator
    - **Сроки разные для:**
        * Успешные трейсы (без ошибок): 7 дней
        * Трейсы с ошибками: 30 дней (для анализа проблем)
        * Критические трейсы (order_overdue, price_calculation_error): 90 дней

4. **Отслеживание изменений Jaeger конфигурации**
    - **Git-based конфиг:** Все правила и фильтры хранятся в Git репозитории
    - **Code review:** Любое изменение требует code review перед merge
    - **Audit log:** Кто, когда и что изменил

### Внешние меры безопасности (для клиентов через Public API)

1. **Трейсы в Public API не доступны клиентам**
    - **Но:** Клиентам доступна информация через обычный API (GET /order/{id}/status)
    - **Трейсы видны только:** Команде "Александрита" для отладки
    - **Если клиент спрашивает:** "Почему мой заказ 2 недели?", support может сказать "У нас техническая проблема на этапе расчёта стоимости, мы работаем над решением" - данные из трейса помогают это определить

2. **Маскирование чувствительных данных**
    - **Примеры маскируемых данных:**
      ```
      - Адреса клиентов: "Russia, Central District" (вместо full address)
      - Email: "**a@***.c***"
      - Phone: "+7 (9**) ***-**-**"
      - Credit card: "****-****-****-4242"
      - Model payload: "<model_hash_abc123>" (вместо binary data)
      ```
    - **Реализация:** OpenTelemetry SpanProcessor с regex правилами

3. **Доступ к трейсам с client_id для B2B партнёров**
    - **Возможное будущее развитие:** Предоставить партнёрам доступ к своим трейсам через отдельный портал
    - **Формат:** read-only доступ только к трейсам, где public_api_client_id == их ID
    - **Реализация:** Jaeger UI с динамическими фильтрами на основе JWT token
    - **На текущий момент:** Не требуется (кроме уведомлений через обычное API)

### Compliance и регуляция

1. **GDPR соответствие (если есть EU клиенты)**
    - **Right to be forgotten:** Если клиент запросит удаление данных, удалить все трейсы с его order_id через script
    - **Data minimization:** Не трейсировать ненужные поля (например, exact timestamp, если достаточно date)
    - **Purpose limitation:** Трейсы используются только для отладки и мониторинга, не для анализа поведения

2. **Логирование compliance**
    - Все изменения в Jaeger конфигурации логируются
    - Все скачивания трейсов (если добавить такую функцию) логируются
