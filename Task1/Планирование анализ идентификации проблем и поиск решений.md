# Планирование: анализ, идентификация проблем и поиск решений

## Часть 1: Идентификация проблемных мест

### Текущие (явные) проблемы

#### 1. **Потеря заказов в системе (критическая)**
- **Описание**: Клиенты не получают уведомления о своих заказах; заказы зависают на неопределённое время
- **Причины**:
  - Асинхронная интеграция через RabbitMQ без гарантий доставки и обработки
  - Отсутствие деадлеттер-очередей и retry-логики
  - Возможные потери сообщений при отказе потребителя
  - Нет механизма reconciliation между системами (CRM и MES работают независимо)
  - Дублирующиеся или неполные данные о заказе в разных системах
- **Масштаб проблемы**: Растёт с каждым месяцем (100+ новых заказов/месяц), теперь критична при работе API
- **Бизнес-влияние**: Потеря контрактов, снижение репутации, отток клиентов

#### 2. **Производительность MES дашборда (высокий приоритет)**
- **Описание**: Первая страница MES долго грузится, даже с фильтром по статусам и пагинацией
- **Текущие попытки решения**: Фильтр + пагинация (неэффективны)
- **Вероятные причины**:
  - Отсутствие индексов в БД на поля фильтра (статус, дата)
  - Загрузка всех данных с сортировкой в памяти приложения вместо БД
  - Отсутствие кэширования часто запрашиваемых данных
  - N+1 запросы в ORM (загрузка заказов + отдельно загрузка связанных данных)
  - Неоптимизированные SQL-запросы
- **Бизнес-влияние**: Операторы теряют время, замедляется распределение заказов (зависит от вознаграждения), операторы видят не самые новые заказы

#### 3. **Долгие циклы CI/CD и нестабильность релизов (высокий приоритет)**
- **Описание**: Задержки релизов на месяц+ из-за обнаружения багов на тестовом окружении; высокие и highest баги блокируют депло
- **Причины**:
  - Ручное E2E-тестирование является bottleneck
  - Отсутствие автоматизированных тестов (unit, интеграционных, E2E)
  - Баги обнаруживаются слишком поздно (на тестовом окружении, а не на ранних этапах)
  - Отсутствие дефектов на ранних стадиях (pull request review, статический анализ)
- **Бизнес-влияние**: Невозможность быстро выпускать исправления и новые функции, накапливаются багги версии

#### 4. **Слабая видимость состояния заказов (средний приоритет)**
- **Описание**: Клиенты жалуются что не знают статус заказа; статусы обновляются асинхронно через RabbitMQ
- **Причины**:
  - Асинхронная обработка событий без уведомлений пользователю
  - Отсутствие real-time уведомлений (вебсокеты, push-notifications)
  - Статус хранится в разных системах (Shop DB vs MES DB) и может быть рассинхронизирован
- **Бизнес-влияние**: Плохой UX, клиенты не знают статус заказа

#### 5. **Масштабируемость API и внутренних систем (критическая)**
- **Описание**: Системы начали получать в 2 раза больше нагрузки после открытия API; возможны отказы
- **Причины**:
  - Single instance для каждого приложения (нет горизонтального масштабирования)
  - Single instance для БД (нет read-replicas)
  - Отсутствие балансировщика нагрузки
  - MES расчёт стоимости занимает до 30 минут на сложные модели — синхронный, блокирует обработку
  - Нет rate-limiting на API
  - Нет очереди для долгоживущих операций (обработка 3D-моделей)
- **Бизнес-влияние**: Система может рухнуть при дальнейшем росте

#### 6. **Отсутствие мониторинга и observability (высокий приоритет)**
- **Описание**: Нет видимости в то, что происходит в системе; баги обнаруживаются только через жалобы клиентов
- **Причины**:
  - Нет логирования ошибок в RabbitMQ обработке
  - Нет метрик о времени обработки, количестве потерь сообщений
  - Нет алертов на аномалии
  - Нет трейсинга между системами
- **Бизнес-влияние**: Невозможно быстро диагностировать проблемы; реагируем на проблемы постфактум

### Потенциальные (скрытые) проблемы

#### 7. **Несогласованность данных между системами (средний приоритет)**
- **Описание**: CRM и MES хранят информацию о заказах независимо; возможна рассинхронизация
- **Причины**:
  - Нет единого источника истины для заказа
  - RabbitMQ может потерять сообщение, на производство пойдёт неполная информация
  - Нет механизма reconciliation
  - CRM создаёт заказ из сообщения MES (в сценарии с API), но нет гарантии обработки этого сообщения
- **Бизнес-влияние**: Производство может начать работать с неполными/неправильными данными; затраты времени

#### 8. **Отсутствие защиты от overload (средний приоритет)**
- **Описание**: Система может быть перегружена запросами от API-пользователей
- **Причины**:
  - Нет rate-limiting на API endpoint
  - Нет backpressure в очередях
  - Синхронный расчёт стоимости (до 30 мин) может заблокировать обработку других заказов
- **Бизнес-влияние**: Legit заказы могут не обработаться из-за spamming/ошибочных запросов

#### 9. **Хранение и обработка 3D-файлов (средний приоритет)**
- **Описание**: Большие 3D-файлы могут перегружать S3 и сетевой трафик
- **Причины**:
  - Неизвестна политика очистки старых файлов
  - Неизвестны ограничения на размер файла
  - Может быть неопасная перекачка файлов между системами
- **Бизнес-влияние**: Дополнительные расходы на хранилище; медленные загрузки

#### 10. **Отсутствие версионирования API (низкий приоритет, но важно)**
- **Описание**: Открыли API для внешних пользователей, но нет стратегии версионирования
- **Причины**:
  - Любое изменение API может сломать интеграции клиентов
- **Бизнес-влияние**: Привязываемся к текущему дизайну API; сложно добавлять функции

#### 11. **Отсутствие аутентификации/авторизации на API (низкий приоритет)**
- **Описание**: Задача говорит "договоримся что проблем нет", но в реальности нужно позаботиться о безопасности API
- **Бизнес-влияние**: Утечка данных; несанкционированный доступ

## Часть 2: Список инициатив (в порядке приоритета)

### Инициатива 1: Гарантированная доставка сообщений в RabbitMQ
**Тип**: Архитектурное изменение  
**Уровень**: Критическая  
**Описание**: Реализовать гарантии доставки и обработки сообщений между CRM и MES
**Решение**:
- Добавить persistent-сообщения в RabbitMQ
- Реализовать retry-логику с exponential backoff
- Добавить deaddletter-очереди для сообщений, которые не обработались после N попыток
- Реализовать транзакционную обработку: сообщение помечается как обработанное только после успешного сохранения в БД
- Добавить логирование всех входящих и исходящих сообщений
**Стоимость**: 1-2 спринта (Java + C# разработчики)  
**Риск**: Высокий риск если не сделать правильно — потеря ещё большего количества заказов

### Инициатива 2: Reconciliation job между системами
**Тип**: Backend feature  
**Уровень**: Критическая  
**Описание**: Ежечасный job, который проверяет консистентность заказов между CRM и MES; исправляет рассинхронизацию
**Решение**:
- Batch job (Quartz scheduler или Spring Batch)
- Сравнивает стейт заказов в обоих системах
- Для рассинхронизированных заказов: отправляет компенсирующее сообщение или создаёт incident
- Логирует все найденные несоответствия для анализа
**Стоимость**: 0.5 спринта (Java разработчик)  
**Зависит от**: Инициативы 1

### Инициатива 3: Асинхронная обработка расчёта стоимости (Job Queue)
**Тип**: Архитектурное изменение  
**Уровень**: Критическая  
**Описание**: Перевести долгоживущий процесс (расчёт стоимости) из синхронного в асинхронный через очередь
**Решение**:
- Создать Job Queue (можно на базе RabbitMQ или Redis) для задач расчёта стоимости
- Создать worker-процессы, которые обрабатывают эти задачи параллельно
- После завершения обновить статус заказа в БД и отправить сообщение в RabbitMQ
- API вернёт 202 Accepted вместо ожидания 30 мин
- Клиент может получить результат через polling или вебсокет
**Стоимость**: 2-3 спринта (C# разработчик, infra, DevOps)  
**Бизнес-результат**: Огромное улучшение UX, масштабируемость, возможность обрабатывать 10x больше заказов

### Инициатива 4: Оптимизация MES дашборда (Performance tuning)
**Тип**: Backend + DB optimization  
**Уровень**: Высокая  
**Описание**: Оптимизировать запросы для получения списка заказов
**Решение**:
- Анализ EXPLAIN PLAN текущих запросов
- Добавить индексы на: `status`, `created_at`, `updated_at`
- Оптимизировать ORM-запросы (избежать N+1)
- Кэширование горячих данных (Redis): сам список заказов, количество заказов по статусам
- Lazy-loading связанных данных
**Стоимость**: 1-2 спринта (Java разработчик + DBA/DevOps)  
**Бизнес-результат**: Первая страница MES будет грузиться мгновенно вместо долгого ожидания

### Инициатива 5: Горизонтальное масштабирование приложений
**Тип**: Infra / DevOps  
**Уровень**: Критическая  
**Описание**: Перейти с single instance на multiple instances с load balancer
**Решение**:
- Развернуть 2-3 инстанса каждого приложения (Shop, CRM, MES)
- Настроить load balancer (NGINX, AWS ALB, Yandex LB)
- Убедиться что приложения stateless (session хранится в Redis или БД)
- Настроить health checks
- Автоматизировать масштабирование (auto-scaling group на базе CPU/memory метрик)
**Стоимость**: 2 спринта (DevOps инженер)  
**Зависит от**: Инициативы 6 (observability)  
**Бизнес-результат**: Система может выдержать 3-5x нагрузку; нет единой точки отказа

### Инициатива 6: Observability (логирование, метрики, трейсинг)
**Тип**: Infra / DevOps  
**Уровень**: Высокая  
**Описание**: Добавить централизованное логирование, метрики и distributed tracing
**Решение**:
- Логирование: ELK stack или Yandex LogStash (Filebeat → Logstash → Elasticsearch)
- Метрики: Prometheus + Grafana
- Трейсинг: Jaeger или Zipkin (OpenTelemetry SDK)
- Алерты на аномалии: Alertmanager
- Dashboard для визуализации состояния системы
**Стоимость**: 2-3 спринта (DevOps инженер + Junior)  
**Бизнес-результат**: Видимость в систему; быстрая диагностика проблем

### Инициатива 7: Автоматизация E2E-тестов
**Тип**: QA automation  
**Уровень**: Высокая  
**Описание**: Заменить ручное E2E-тестирование автоматизированными тестами
**Решение**:
- Использовать Selenium, Cypress или Playwright
- Написать тесты для основных сценариев (create order, upload file, assign to operator и т.д.)
- Интегрировать в CI/CD pipeline
- Запускать на каждый PR и перед релизом
**Стоимость**: 2-3 спринта (QA инженер, немного помощи от фронтенд)  
**Зависит от**: Инициативы 8  
**Бизнес-результат**: Баги обнаруживаются раньше; релизы становятся быстрее

### Инициатива 8: Расширение unit-тестов и добавление интеграционных тестов
**Тип**: Code quality  
**Уровень**: Высокая  
**Описание**: Увеличить покрытие unit-тестов; добавить интеграционные тесты для RabbitMQ
**Решение**:
- Unit-тесты для бизнес-логики (>80% покрытие)
- Интеграционные тесты для RabbitMQ и DB взаимодействия
- Используется TestContainers для изоляции (PostgreSQL, RabbitMQ в контейнерах)
- Запуск на каждый PR; блокирование мерджа при падении тестов
**Стоимость**: 2 спринта (Java + C# разработчики)  
**Бизнес-результат**: Меньше багов в прод; быстрее выловить регрессии

### Инициатива 9: Rate-limiting на API
**Тип**: Backend feature  
**Уровень**: Средняя  
**Описание**: Защитить API от перегрузки через rate-limiting
**Решение**:
- Реализовать rate-limiting на уровне API Gateway или в приложении
- Per-client rate-limit (по API key или IP)
- Вернуть 429 Too Many Requests при превышении лимита
- Логировать все rate-limited запросы
**Стоимость**: 0.5 спринта (Java разработчик)

### Инициатива 10: Реал-тайм уведомления для клиентов (WebSocket)
**Тип**: Frontend + Backend feature  
**Уровень**: Средняя  
**Описание**: Добавить real-time уведомления об изменении статуса заказа
**Решение**:
- WebSocket сервер (или Socket.io) в Java/C#
- Клиент подписывается на обновления заказа
- При изменении статуса через RabbitMQ отправляем событие в WebSocket
- Frontend обновляет UI без перезагрузки
**Стоимость**: 1.5 спринта (фронтенд + бэкенд)  
**Зависит от**: Инициативы 1  
**Бизнес-результат**: Клиенты видят обновления в реальном времени

### Инициатива 11: Versioning и документация API
**Тип**: Backend feature  
**Уровень**: Низкая (но важно для долгосрочности)  
**Описание**: Добавить версионирование API; автогенерируемую документацию (OpenAPI/Swagger)
**Решение**:
- Добавить версию в URL: `/api/v1/...`
- Использовать OpenAPI 3.0 specification
- Интегрировать Swagger UI для интерактивной документации
- Документировать все endpoints, параметры, ошибки
**Стоимость**: 1 спринт (Java разработчик)

### Инициатива 12: Data retention и cleanup для 3D-файлов
**Тип**: Infra feature  
**Уровень**: Низкая  
**Описание**: Реализовать политику удаления старых файлов и архивирования
**Решение**:
- Удалять 3D-файлы спустя X дней после завершения заказа
- Архивировать на Glacier для компания/финансовых целей
- Логировать все удаления
**Стоимость**: 0.5 спринта (DevOps)

## Часть 3: Приоритизация и планирование

### Рассуждение о приоритетах

**Текущее состояние**: Система теряет заказы, падает производительность, выпускать релизы сложно и долго. Компания теряет контракты.

**Критерии приоритизации**:
1. **Влияние на бизнес**: Прямое влияние на доход, репутацию, удержание клиентов
2. **Срочность**: Насколько быстро нужно решить, чтобы остановить кровотечение
3. **Риск системы**: Возможность полного отказа системы
4. **Зависимости**: Какие инициативы нужны как основа для других

### Три приоритетные инициативы на следующие 6 месяцев

#### Приоритет 1: **Гарантированная доставка + Reconciliation** (Инициативы 1, 2)
**Почему это критично**:
- Это **прямая причина потери заказов** — главная проблема компании
- Без этого все остальные улучшения будут не сильно полезными
- Бизнес готов к этому изменению (это не требует изменений в процессах)
- Фиксирует проблему "на корню", а не симптомы

**Что входит**:
- Persistent сообщения в RabbitMQ с retry-логикой и DLQ
- Транзакционная обработка на обоих концах (Shop API → RabbitMQ → CRM API и CRM API → RabbitMQ → MES API)
- Reconciliation job (ежечасный) для проверки консистентности
- Логирование всех сообщений для аудита и отладки

**Бизнес-результат**:
- ✓ 95%+ гарантия доставки сообщений
- ✓ Возможность восстановить потерянные заказы через reconciliation job
- ✓ Прозрачность в процесс обработки заказов

**Сроки**: 2-3 спринта  
**Команда**: 2 Java разработчика + 1 C# разработчик + 1 DevOps (для инфраструктуры мониторинга)

**Зависимости**: Нет

---

#### Приоритет 2: **Асинхронная обработка расчётов стоимости** (Инициатива 3)
**Почему это критично**:
- **Масштабируемость**: Синхронный расчёт (до 30 мин) является bottleneck для всей системы
- **Пользовательский опыт**: API вернёт результат за миллисекунды вместо 30 минут
- **Надёжность**: Большие задачи не заблокируют обработку других заказов
- Необходимо для поддержки дальнейшего роста (100+ новых заказов в месяц)

**Что входит**:
- Job Queue на базе RabbitMQ (или Redis)
- Worker processes для обработки задач (могут работать параллельно на разных инстансах)
- Webhook-like callback когда задача готова (отправляет сообщение в RabbitMQ для CRM)
- Async API endpoint возвращает 202 Accepted + Job ID

**Бизнес-результат**:
- ✓ Можем обрабатывать 5-10x больше заказов одновременно
- ✓ API клиенты не зависают ожидая расчёта
- ✓ Операторы видят заказы быстрее (не ждут расчёта для каждого заказа)

**Сроки**: 2-3 спринта  
**Команда**: 1 C# разработчик (MES) + 1 DevOps

**Зависимости**: Желательно Инициатива 1 (чтобы callback работал надёжно)

---

#### Приоритет 3: **Observability (логирование + метрики)** (Инициатива 6)
**Почему это критично**:
- **Видимость**: Без этого невозможно быстро диагностировать проблемы
- **Основа для других**: Масштабирование, оптимизация и мониторинг требуют метрик
- **Превентивные алерты**: Можем обнаружить проблемы до того, как они повлияют на пользователей
- **Бизнес-разговоры**: Данные для обоснования необходимости инфраструктурных изменений
- **Трейсинг**: Осуществление трейсинга для отлавливания ошибок 

**Что входит**:
- Centralized logging (ELK stack или Yandex Cloud)
- Metrics collection (Prometheus)
- Dashboards (Grafana)
- Distributed tracing (Jaeger)
- Alert rules на основе SLO

**Бизнес-результат**:
- ✓ MTTR (Mean Time To Repair) падает с часов на минуты
- ✓ Видимость в производительность каждой части системы
- ✓ Обоснованные решения по оптимизации/масштабированию

**Сроки**: 2-3 спринта  
**Команда**: 1 DevOps инженер + 1 Junior DevOps

**Зависимости**: Нет

---

## Часть 4: Что НЕ входит в первые 6 месяцев

1. **WebSocket реал-тайм уведомления** — Nice to have, но не критично для функциональности. Можно сделать polling.
2. **Versioning API** — Может быть сделано после того как стабилизируется API в прод.
3. **Data retention для 3D-файлов** — Низкий приоритет, может быть отложено.
4. **Автоматизированное горизонтальное масштабирование** — Сначала нужна observability, потом можно добавить auto-scaling.
