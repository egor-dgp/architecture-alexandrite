# Архитектурное решение по кешированию для компании «Александрит»

## 1. Анализ системы и определение точек кеширования

### Текущие проблемы производительности

**Проблема 1: Медленная работа MES для операторов**
- Первая страница (дашборд заказов) загружается медленно
- Операторы жалуются на задержку при загрузке списка заказов в работе
- Причина: на каждый запрос выполняется фильтрация по статусам, пагинация требует множества запросов в БД

**Проблема 2: Медленное выполнение заказов**
- Клиенты получают заказы с опозданием
- Прямая связь: MES может считать цену заказа 2-30 минут (зависит от сложности модели)
- Причина: повторяющиеся расчеты одних и тех же параметров для похожих моделей

**Проблема 3: Нагрузка на внешний API**
- Компания открыла API для партнеров
- Каждый партнер повторяет одни и те же запросы (список товаров, статусы заказов)
- Причина: отсутствие кеширования на стороне API

### Диагностика узких мест

**MES API - операция расчета цены:**
- Входные параметры: 3D модель (количество полигонов, размер файла)
- Выходные данные: стоимость производства
- Характеристика: детерминированная функция (один и тот же input = один и тот же output)
- Частота обращений: каждый заказ → отличный кандидат для кеша

**MES UI - дашборд заказов:**
- Входные параметры: фильтр по статусам, пагинация (offset/limit)
- Выходные данные: список заказов с метаданными
- Характеристика: часто изменяется (статус меняется при работе оператора)
- Частота обращений: каждые 10 секунд при работе оператора
- Кеширование: возможно с коротким TTL (10-30 сек)

**Shop API - список товаров:**
- Входные параметры: категория, параметры фильтрации
- Выходные данные: каталог товаров с ценами
- Характеристика: очень редко меняется
- Частота обращений: высокая (каждый клиент при входе на сайт)
- Кеширование: идеальный кандидат (TTL часы)

**RabbitMQ интеграция:**
- Сообщения между CRM и MES о смене статуса
- Характеристика: обновляют состояние (не кешируются напрямую)
- Кеширование: кешируем результаты, не сами сообщения

## 2. Мотивация внедрения кеширования

### Почему кеширование критично для «Александрита»

**Текущая ситуация:**
- MES затрачивает 2-30 минут на расчет цены за один заказ
- Дашборд заказов грузится медленно, операторы не хотят работать с системой
- Открытие API не масштабируется — партнеры получают задержки

**Что решит кеширование:**

1. **Ускорение расчета цены (Price Calculation)**
    - Без кеша: 2-30 минут на расчет
    - С кешем: 1-100 мс при попадании в кеш (~90% заказов похожи)
    - Результат: в 1000x раз быстрее для повторяющихся моделей

2. **Ускорение загрузки дашборда MES**
    - Без кеша: 5-15 сек для загрузки 200 заказов
    - С кешем: 100-500 мс при кешировании списков
    - Результат: более комфортная работа операторов, выше производительность

3. **Масштабируемость API для партнеров**
    - Без кеша: нужно масштабировать инфраструктуру под каждого нового партнера
    - С кешем: один запрос = один расчет, последующие = из кеша
    - Результат: экономия на инфраструктуре, повышение доступности API

### Целевые метрики

| Метрика | До кеширования | После кеширования | Причина улучшения |
|---------|----------|-------------|-------------------|
| Время расчета цены (среднее) | 5-10 мин | <1 сек (для кешированных) | Кеш в памяти вместо расчета |
| Время загрузки дашборда MES | 10-15 сек | <500 мс | Кеш запросов к БД |
| Количество запросов в БД MES | 500k/день | 100k/день | Кеширование запросов |
| Процент неудовлетворенных клиентов | ~15% | < 2% | Быстрое выполнение |
| Пропускная способность API | ~100 реквестов/сек | ~10k реквестов/сек | Кеширование покрывает нагрузку |

### Элементы системы для кеширования (приоритет)

**Волна 1 - КРИТИЧНАЯ (спринты 1-2):**
1. **Price Calculation Cache** (MES API)
    - Кешировать результаты расчета цены по хэшу 3D модели
    - TTL: бесконечный (цена не меняется для одной модели)
    - Размер: ~100 MB для 50k моделей

2. **Order List Cache** (MES UI)
    - Кешировать список заказов по статусам
    - TTL: 30 сек (статусы меняются)
    - Размер: ~10 MB

**Волна 2 - ВЫСОКИЙ ПРИОРИТЕТ (спринты 3-4):**
3. **Product Catalog Cache** (Shop API)
    - Кешировать каталог товаров
    - TTL: 1 час (редко меняется)
    - Размер: ~50 MB

4. **Order Details Cache** (Shop API + CRM)
    - Кешировать детали заказа
    - TTL: 5 мин (может меняться статус)
    - Размер: ~10 MB

**Волна 3 - ОПЦИОНАЛЬНОЕ (спринты 5+):**
5. **API Partner Rate Limiting Cache**
    - Отслеживание квот API партнеров
    - TTL: 60 сек
    - Размер: ~1 MB

## 3. Предлагаемое решение

### 3.1 Выбор типа кеширования

#### Вариант А: Клиентское кеширование (HTTP Cache-Control)
**Преимущества:**
- Работает в браузере, не требует серверных ресурсов
- Встроено в HTTP протокол
- Автоматически работает для статических ресурсов

**Недостатки:**
- Не подходит для динамических API (список заказов меняется каждые 30 сек)
- Не помогает для операторов MES (нужна мгновенная обновляемость)
- Не масштабирует нагрузку на сервер (каждый клиент все равно делает запрос)

#### Вариант Б: Серверное кеширование (Redis)
**Преимущества:**
- Подходит для динамических данных
- Центральное хранилище, видимо для всех клиентов
- Быстрое получение популярных данных
- Поддерживает сложные сценарии инвалидации

**Недостатки:**
- Требует дополнительной инфраструктуры (Redis сервер)
- Нужно обрабатывать кеш-промахи

### **ВЫБРАННЫЙ ПОДХОД: Гибридное решение (HTTP Cache-Control + Redis)**

**Комбинация оптимальна, потому что:**
1. HTTP кеш для статических ресурсов (Product Catalog) - экономит трафик
2. Redis для динамических операций (Price Cache, Order Lists) - масштабирует нагрузку
3. Разные TTL для разных типов данных

### 3.2 Выбор паттернов кеширования

#### Сценарий 1: Price Calculation Cache (MES API)

**Характеристика:**
- Запрос: 3D модель (параметры → file_hash)
- Ответ: стоимость производства
- Изменяемость: НЕ изменяется (детерминированная функция)
- Частота обращений: HIGH (каждый заказ)

**ВЫБРАННЫЙ ПАТТЕРН: Cache-Aside**

```
Поток:
1. Оператор запрашивает расчет цены для модели X (hash = "ABC123")
2. MES API ищет в Redis по ключу "price:ABC123"
3. Если найдено → возвращает из Redis (< 1 мс)
4. Если не найдено (cache miss) → выполняет расчет (2-30 мин)
5. Сохраняет результат в Redis с TTL = бесконечный
6. Возвращает результат клиенту
```

**Почему Cache-Aside подходит лучше:**

| Паттерн | Применимость | Причина непригодности |
|--------|--------------|----------------------|
| **Cache-Aside ✓** | Подходит     | Простая логика, детерминированная функция, возможны промахи, коротко обрабатываются |
| Read-Through | Худше        | Требует изменения логики MES, сложнее отладить |
| Refresh-Ahead | Не подходит  | Нет нужны в предварительной загрузке (модели новые) |

**Особенности реализации:**
- Ключ: `price:{model_hash}` (например: `price:abc123def456`)
- Значение: JSON с деталями расчета (цена, время, материал)
- TTL: бесконечный (или 1 год для очистки старых)
- Инвалидация: только при изменении формулы расчета (редко, программная)

---

#### Сценарий 2: Order List Cache (MES UI)

**Характеристика:**
- Запрос: фильтр по статусам (например: MANUFACTURING_STARTED)
- Ответ: список заказов с метаданными
- Изменяемость: ЧАСТО (статус меняется каждые 30 сек)
- Частота обращений: ULTRA HIGH (каждые 10 сек от каждого оператора)

**ВЫБРАННЫЙ ПАТТЕРН: Cache-Aside с коротким TTL**

```
Поток:
1. Оператор открывает дашборд с фильтром status=MANUFACTURING_STARTED
2. MES UI запрашивает у API: GET /api/orders?status=MANUFACTURING_STARTED&offset=0&limit=50
3. MES API ищет в Redis по ключу "orders:status:MANUFACTURING_STARTED:0:50"
4. Если найдено (< 30 сек назад) → возвращает из Redis (< 10 мс)
5. Если не найдено или TTL истек → запрашивает из БД MES DB
6. Сохраняет в Redis с TTL = 30 сек
7. Возвращает результат клиенту
8. Оператор видит данные быстро, даже если обновление 30 сек свежести
```

**Почему Cache-Aside подходит лучше:**

| Паттерн | Применимость | Причина непригодности |
|--------|-------------|----------------------|
| **Cache-Aside ✓** | Подходит | Динамические данные, короткий TTL, операторы не требуют 100% свежести |
| Write-Through | Хуже | Замедлит операцию смены статуса на 100+ мс (ожидание синхронной записи) |
| Write-Behind | Возможно | Сложнее реализовать, может привести к потере обновлений |
| Refresh-Ahead | Подходит частично | Можно использовать для предварительной загрузки часто используемых фильтров |

**Особенности реализации:**
- Ключ: `orders:{status}:{offset}:{limit}` (например: `orders:MANUFACTURING_STARTED:0:50`)
- Значение: JSON массив с заказами
- TTL: 30 сек (баланс между свежестью и производительностью)
- Инвалидация: временная (TTL) + программная при смене статуса

---

#### Сценарий 3: Product Catalog Cache (Shop API)

**Характеристика:**
- Запрос: категория товара, параметры фильтрации
- Ответ: каталог товаров с описаниями
- Изменяемость: РЕДКО (администратор добавляет товары)
- Частота обращений: HIGH (каждый клиент при входе)

**ВЫБРАННЫЙ ПАТТЕРН: Cache-Aside с длительным TTL + HTTP Cache-Control**

```
Поток:
1. Клиент открывает сайт, запрашивает каталог товаров
2. Frontend проверяет HTTP кеш браузера
3. Если есть и не истек → использует локальный кеш
4. Если нет или истек → запрашивает у Shop API
5. Shop API ищет в Redis по ключу "catalog:{category}:{filters_hash}"
6. Если найдено → возвращает из Redis с заголовком Cache-Control: max-age=3600
7. Если не найдено → запрашивает из БД, сохраняет в Redis с TTL = 1 час
8. Браузер кеширует результат на 1 час
9. При следующем запросе браузер использует локальный кеш
```

**Почему Cache-Aside подходит лучше:**

| Паттерн | Применимость | Причина непригодности |
|--------|-------------|----------------------|
| **Cache-Aside ✓** | Подходит | Статические данные, высокая часто запрашиваемость, можно еще кешировать в браузере |
| Read-Through | Нейтрально | Можно использовать, но добавляет сложность |
| Refresh-Ahead | Подходит | Можно использовать вместе (загружать популярные категории заранее) |

**Особенности реализации:**
- Ключ: `catalog:{category_id}:{filters_hash}`
- Значение: JSON с товарами и ценами
- TTL: 3600 сек (1 час)
- HTTP заголовок: `Cache-Control: max-age=3600, public`
- Инвалидация: временная (TTL) + программная при добавлении товара

### 3.3 Диаграмма последовательности операций

#### Операция 1: Чтение списка заказов (MES Дашборд)

```
Оператор                    MES UI              MES API             Redis              MES DB
   |                          |                   |                    |                  |
   |--- Открыть дашборд ----->|                   |                    |                  |
   |                          |--- GET /orders?status=MANUFACTURING_STARTED --->|
   |                          |                   |                    |
   |                          |                   |--- Ищет "orders:MANUFACTURING_STARTED:0:50" --->|
   |                          |                   |<------- HIT (30s свежести) ----------|
   |                          |<--- Orders JSON (из кеша) ---|
   |<--- Дашборд загружен за <500ms ---|
   |
   |[через 20 секунд]
   |--- F5 (обновить) -------->|
   |                          |
   |                          |--- GET /orders?status=MANUFACTURING_STARTED --->|
   |                          |                   |                    |
   |                          |                   |--- Ищет "orders:MANUFACTURING_STARTED:0:50" --->|
   |                          |                   |<------- HIT (10s свежести) ----------|
   |                          |<--- Orders JSON (из кеша) ---|
   |<--- Дашборд обновлен за <500ms ---|
   |
   |[через 40 секунд с момента первой загрузки, TTL истек]
   |
   |                          |--- GET /orders?status=MANUFACTURING_STARTED --->|
   |                          |                   |                    |
   |                          |                   |--- Ищет "orders:MANUFACTURING_STARTED:0:50" --->|
   |                          |                   |<------- MISS (TTL истек) ----------|
   |                          |                   |                    |
   |                          |                   |--- SELECT * FROM orders WHERE status='MANUFACTURING_STARTED' --->|
   |                          |                   |<--- Orders (из БД) ---|
   |                          |                   |                    |
   |                          |                   |--- SET "orders:MANUFACTURING_STARTED:0:50" TTL=30 --->|
   |                          |<--- Orders JSON ---|
   |<--- Дашборд обновлен за 2-3 сек ---|
```

**Ключевые моменты:**
- При попадании в кеш: <500 мс
- При промахе (первый раз или истек TTL): 2-3 сек
- TTL 30 секунд — баланс между производительностью и свежестью

```
Оператор              MES UI          MES API          Redis            RabbitMQ        CRM API         MES DB

   |-- Клик "Взять в работу" -->|      |                |                 |               |              |
   |                   |---- POST /orders/123/start ---->|                 |                 |
   |                   |               |                |                 |               |              |

   |                   |               |                |                 |               |              |
   |                   |               |--- Отправить сообщение в очередь --->|              |

   |                   |               |<--- OK ---|

   |<--- Статус обновлен ---|

   |                   |               |                |                 |               |<--- Процесс сообщение
   |                   |               |                |                 |               |--- Обновить заказ
   |                   |               |                |                 |               |--- Инвалидировать кеш
```

**Ключевые моменты:**
- Запись всегда идет в БД (синхронно)
- Параллельно происходит инвалидация кеша
- Сообщение отправляется в очередь (асинхронно)
- CRM получит обновление через RabbitMQ и обновит свой кеш

### 3.4 Стратегия инвалидации кеша

#### Анализ доступных стратегий

**Стратегия 1: Временная инвалидация (TTL)**

```
Механизм: Redis автоматически удаляет ключ через N секунд

Пример для Order List Cache:
key: "orders:MANUFACTURING_STARTED:0:50"
TTL: 30 сек
→ Ключ существует 30 сек, затем удаляется

Применимость:
✓ Простая реализация
✓ Не требует дополнительной логики
✗ На 29 сек может быть свежесть данных
✗ При быстрых обновлениях может быть стаб
```

**Стратегия 2: Инвалидация по событию (программная)**

```
Механизм: При смене статуса заказа → инвалидировать кеш

Пример для Order List Cache:
ORDER_CREATED → DEL "orders:*"
ORDER_APPROVED → DEL "orders:*"
ORDER_STARTED → DEL "orders:*"
PRICE_CALCULATED → DEL "price:*"

Применимость:
✓ Гарантирует свежесть
✓ Минимизирует промахи
✗ Требует изменения логики обновлений
✗ Если забыть инвалидировать → данные будут стаб
```

**Стратегия 3: Инвалидация по ключу (селективная)**

```
Механизм: Инвалидировать только конкретные ключи

Пример для изменения статуса заказа #123:
ORDER_STATUS_CHANGED(order_id=123)
→ DEL "orders:MANUFACTURING_STARTED:*"
→ DEL "orders:*"  (более широкая инвалидация)

Применимость:
✓ Точная инвалидация
✓ Не теряет другие кешированные данные
✗ Может быть сложной в реализации
```

**Стратегия 4: Гибридная (TTL + программная)**

```
Механизм: Комбинация TTL и событийной инвалидации

Пример:
- Order List: TTL 30 сек + DEL при смене статуса
- Price Cache: TTL 1 год (очень редко меняется) + DEL при обновлении формулы

Применимость:
✓ Баланс между производительностью и свежестью
✓ Страховка от забытой инвалидации
✓ Разные стратегии для разных типов данных
✗ Требует координации двух механизмов
```

#### Выбранная стратегия: Гибридная (TTL + программная инвалидация)

**Рекомендуемая конфигурация по типам кеша:**

| Тип кеша | TTL | Программная инвалидация | Стратегия |
|---------|-----|------------------------|-----------|
| **Price Calculation** | 1 год | При обновлении формулы расчета | TTL + программная |
| **Order List** | 30 сек | DEL `orders:*` при смене статуса | TTL + программная |
| **Order Details** | 5 мин | DEL при смене статуса | TTL + программная |
| **Product Catalog** | 1 час | DEL при добавлении/удалении товара | TTL + HTTP Cache-Control |
| **API Partner Quota** | 60 сек | Не требуется | TTL только |

**Почему эта стратегия лучше других:**

| Аспект | TTL только | Программная только | Гибридная (ВЫБРАНА) |
|--------|---------|-------------------|------------------|
| **Простота** | Очень простая | Средняя сложность | Средняя сложность |
| **Гарантия свежести** | 50% (может быть стаб) | 100% | 95% (страховка на случай забытой инвалидации) |
| **Производительность** | Отличная (автоматическая очистка) | Хорошая | Отличная |
| **Отказоустойчивость** | Если забыть DEL → данные застарят | Если забыть DEL → данные застарят | Если забыть DEL → есть TTL |
| **Сложность в поддержке** | Минимальная | Средняя (нужно помнить о DEL) | Средняя |
| **Масштабируемость** | Хорошая | Хорошая | Отличная |
