# Архитектурное решение по логированию для компании «Александрит»

## Анализ системы и требования к логированию

### Текущее состояние системы
Система состоит из трёх основных приложений:
- **Онлайн-магазин** (Vue + Java Spring Boot) — точка входа для клиентов
- **CRM** (Vue + Java Spring Boot) — управление клиентами и заказами
- **MES** (React + C#) — производственная система управления

Ключевая характеристика: интеграция между системами осуществляется через **RabbitMQ**, который является критичной точкой в обработке потока заказов.

### Критические проблемы, требующие логирования
1. **Потеря заказов** — клиенты не получают информацию о выполнении заказов
2. **Медленная загрузка MES** — операторы ждут на первой странице
3. **Проблемы с интеграцией API** — нет видимости в поток данных между системами
4. **Невозможность быстрой диагностики** — разбор ошибок требует часов общения с клиентами

### Динамика развития проблемы
- Линейный рост заказов (~100 в месяц)
- Открытие API привело к экспоненциальному росту нагрузки
- Потеря крупных контрактов из-за недостаточной видимости и скорости обработки

## Другие уровни логирования

### WARN (предупреждение)
Используется в следующих случаях:

- **Медленная обработка заказа**: обработка заказа превышает установленный порог времени (например, >5 минут)
  ```
  WARN: Order processing time exceeded 300s for order_id=ORDER_123
  ```

- **Высокая очередь сообщений**: количество необработанных сообщений превышает пороговое значение
  ```
  WARN: RabbitMQ queue depth exceeded 1000 for queue_name=mes.orders
  ```

- **Предупреждение о месте на диске**: использование дискового пространства логов превышает 80%
  ```
  WARN: Log storage usage at 82% capacity
  ```

- **Низкие ресурсы**: CPU или память приближаются к лимитам
  ```
  WARN: MES API memory usage at 85%
  ```

- **Частые повторы операции**: операция была повторена >3 раз подряд
  ```
  WARN: Price calculation retry count exceeded 3 for order_id=ORDER_456
  ```

- **Истечение лицензий или сертификатов**
  ```
  WARN: SSL certificate expires in 15 days
  ```

### ERROR (ошибка)
Используется для сбойных ситуаций, которые приводят к неудачной операции:

- **Ошибка расчета стоимости**: система не смогла рассчитать цену
  ```
  ERROR: Price calculation failed for order_id=ORDER_789, reason=model_parsing_error
  Stack trace: [полная информация об ошибке]
  ```

- **Сбой доставки сообщений**: RabbitMQ не доставил сообщение после повторных попыток
  ```
  ERROR: Message delivery failed for correlation_id=CORR_123 after 5 retries
  Last error: Connection refused
  ```

- **Ошибка доступа к БД**: не удалось выполнить операцию с базой данных
  ```
  ERROR: Database connection failed for shop_db, error=timeout
  ```

- **Ошибка API**: внешний API вернул ошибку
  ```
  ERROR: 3D file storage API returned error 503 for order_id=ORDER_234
  ```

- **Критичные ошибки обработки заказа**
  ```
  ERROR: Order status transition invalid: from=SUBMITTED to=SHIPPED without manufacturing approval
  ```

### DEBUG (отладка)
Используется при разработке и диагностике сложных проблем:

- **Детали обработки запроса**: параметры, преобразования данных
  ```
  DEBUG: Processing order submission with params: {customer_id: 123, model_size_mb: 45.6}
  ```

- **Промежуточные значения**: переменные в ходе выполнения
  ```
  DEBUG: Polygon count calculated: 15234, complexity_estimate: high
  ```

- **Внутренние состояния**: информация о кеше, очередях
  ```
  DEBUG: Cache state - active_orders: 234, failed_orders: 12
  ```

- **Детали сетевых вызовов**: заголовки, тела запросов (без чувствительных данных)
  ```
  DEBUG: HTTP request to MES API: method=POST, endpoint=/price-calculate, timeout=300s
  ```

## Мотивация внедрения логирования

### Почему логирование критично для «Александрита»

**Текущая ситуация:** Компания потеряла несколько крупных контрактов из-за неспособности быстро диагностировать проблемы с заказами. Клиенты жалуются на несоответствия между предполагаемым временем обработки и фактическим, а команда не имеет данных для проверки статуса заказа.

**Что даст логирование:**
1. **Видимость в систему** — полная траектория каждого заказа от создания до доставки
2. **Быстрая диагностика** — сокращение времени разбора инцидентов с часов до минут
3. **Доказательства для клиентов** — конкретные логи, доказывающие выполнение работы
4. **Основа для оптимизации** — данные для анализа узких мест

### Ключевые технические и бизнес-метрики

| Метрика | Текущее состояние | Целевое состояние | Влияние логирования |
|---------|-------------------|-------------------|----------------------|
| **Среднее время диагностики инцидента** | 4-6 часов | < 15 минут | Прямое — логи содержат полную информацию о проблеме |
| **Время обработки заказа (среднее)** | ~5 дней | ~3 дня | Опосредованное — логи покажут узкие места |
| **Количество потерянных заказов в месяц** | ~3-5 (по жалобам) | 0 | Высокое — логи отследят каждый заказ |
| **Время обработки API запроса (P95)** | ~5-10 сек | < 2 сек | Опосредованное — выявление медленных операций |
| **Количество повторных контактов клиента** | ~40% заказов | < 5% | Высокое — клиенты смогут сами проверить статус |
| **Retention крупных клиентов** | 60% (падающий тренд) | > 95% | Высокое — улучшение надежности восстанавливает доверие |
| **Время разработки нового функционала** | Замедлено из-за инцидентов | На графике | Опосредованное — меньше пожаротушения |
| **Скорость маркетинга нового API** | Невозможна | Планируется | Высокое — логирование обеспечит надежность для новых партнеров |

## Приоритизация систем для внедрения логирования

### Первая волна (спринты 1-2)
**Приоритет: КРИТИЧНЫЙ**

#### 1. RabbitMQ + CRM API интеграция
**Почему:** Это основная точка отказа системы. Если сообщение потеряется в очереди, заказ исчезнет.
- Логирование всех сообщений в RabbitMQ (publish/consume)
- Отслеживание ошибок доставки
- Корреляция сообщений между CRM и MES

**Ожидаемый результат:** Выявление потерянных заказов, видимость в поток данных между системами

#### 2. MES API (логирование расчета стоимости)
**Почему:** Медленная обработка (2-30 минут) — основная жалоба операторов.
- Логирование начала и окончания расчета
- Отслеживание количества полигонов и времени обработки
- Выявление аномалий (почему один заказ 2 минуты, другой 30 минут)

**Ожидаемый результат:** Выявление узких мест, оптимизация алгоритма расчета

#### 3. Order Status Transitions (CRM + MES)
**Почему:** Неясно, на каком этапе застревают заказы.
- Логирование каждого изменения статуса
- Временные метки между переходами
- Отслеживание аномальных переходов (прямой скачок без промежуточных этапов)

**Ожидаемый результат:** Точное определение стадии проблемы (создание, оценка, производство, доставка)

### Вторая волна (спринты 3-4)
**Приоритет: ВЫСОКИЙ**

#### 4. Онлайн-магазин (Shop API)
- Логирование создания заказов
- Отслеживание загрузок файлов (размер, формат, хэш)
- Логирование ошибок валидации

**Почему вторая волна:** Проблемы чаще начинаются после создания заказа, но видимость в магазине поможет исключить клиентские ошибки.

#### 5. API доступ (для внешних партнеров)
- Логирование всех вызовов API
- Отслеживание использования квоты
- Выявление аномальных паттернов (признаки DDoS)

**Почему вторая волна:** Это будет актуально после стабилизации внутренних процессов.

### Третья волна (спринты 5+)
**Приоритет: СРЕДНИЙ**

#### 6. Аутентификация и доступ
- Логирование входов операторов в MES
- Отслеживание изменения данных (кто что менял)

#### 7. Аналитические логи
- Поведение пользователей на сайте
- Анализ конверсии в заказ
- A/B тестирование новых функций

## Предлагаемое решение

### Архитектура логирования

```
┌─────────────────────────────────────────────────────────────────┐
│                        Логирующие приложения                    │
├─────────────────────────────────────────────────────────────────┤
│  Shop API     │  CRM API      │  MES API      │  RabbitMQ        │
│  (Java)       │  (Java)       │  (C#)         │  (broker)        │
│               │               │               │                  │
│ SLF4J logs    │ SLF4J logs    │ Serilog logs  │ Built-in logging │
└────┬──────────┴────┬──────────┴────┬──────────┴────┬─────────────┘
     │               │                │              │
     └───────────────┴────────────────┴──────────────┘
                     │
         ┌───────────▼──────────────┐
         │   Logstash / Filebeat    │
         │   (сбор логов)           │
         └───────────┬──────────────┘
                     │
         ┌───────────▼──────────────┐
         │  Elasticsearch           │
         │  (хранилище)             │
         │                          │
         │ Индексы по системам:     │
         │ - shop-logs-*            │
         │ - crm-logs-*             │
         │ - mes-logs-*             │
         │ - rabbitmq-logs-*        │
         └───────────┬──────────────┘
                     │
         ┌───────────┴────────────┬──────────────────┐
         │                        │                  │
    ┌────▼────┐          ┌────────▼──────┐   ┌──────▼──────┐
    │ Kibana  │          │ Alertmanager  │   │ OpenSearch  │
    │ (UI)    │          │ (алертинг)    │   │ (аналитика) │
    └─────────┘          └───────────────┘   └─────────────┘
```

### Технологический стек

| Компонент | Технология | Причина выбора |
|-----------|-----------|-----------------|
| **Сбор логов** | Filebeat/Logstash | Легко интегрируется с Java и C#, меньше ресурсов чем ELK полностью |
| **Хранилище** | Elasticsearch | Стандарт де-факто, быстрый поиск, встроенные возможности аналитики |
| **Визуализация** | Kibana | Встроена с Elasticsearch, удобна для быстрого поиска |
| **Трейсинг** | OpenTelemetry + Jaeger | Стандарт индустрии, поддержка во всех фреймворках |
| **Алертинг** | Alertmanager / Kibana Alerts | Интегрирован с Prometheus/Elasticsearch |

### Требуемые компоненты в архитектуре

#### 1. Логирующие библиотеки в приложениях

**Для Java (Shop API, CRM API):**
```
Зависимости:
- SLF4J (фасад логирования)
- Logback (реализация, встроена в Spring Boot)
- Logstash logback encoder (форматирование в JSON)
```

**Для C# (MES API):**
```
Зависимости:
- Serilog (современный логгер для .NET)
- Serilog.Sinks.Http (отправка в Logstash)
- Serilog.Structured (структурированное логирование)
```

#### 2. Новые микросервисы в инфраструктуре

| Сервис | Назначение | Масштаб |
|--------|-----------|---------|
| Filebeat | Сбор логов из файлов | 3 инстанса (один на каждый сервер приложения) |
| Logstash | Фильтрация и парсинг логов | 2 инстанса (масштабируемые за счет очереди) |
| Elasticsearch | Хранилище | 3 узла (надежность и масштабируемость) |
| Kibana | Веб-интерфейс | 1 инстанс (можно дублировать для HA) |
| OpenTelemetry Collector | Сбор трейсов | 2 инстанса |
| Jaeger | Хранение трейсов | 1 инстанс (можно масштабировать) |

## Политика безопасности логов

### Обработка чувствительных данных

#### Какие данные считаются чувствительными
1. **Персональные данные клиентов** (ФИО, email, телефон, адрес доставки)
2. **Данные платежей** (номера карт, CVV, суммы транзакций)
3. **Коммерческие тайны** (стоимость материалов, маржа, формулы расчета)
4. **Технические учетные данные** (пароли, API ключи, токены)

#### Стратегия маскирования

**Уровень 1: В приложениях (на уровне SDK)**
```
При логировании масксировать:
- Email: first_letter***@domain.com (a***@gmail.com)
- Телефон: +7 (***) *** 12 34
- Адрес: только город и регион
- Номер карты: ****-****-****-1234
- Сумма платежа: только диапазон (100-500 RUB)
```

**Уровень 2: В Logstash (на уровне сборки)**
```
Дополнительные фильтры для перестраховки:
- Regex фильтры на известные паттерны карт
- Удаление параметров с префиксом "password", "secret", "token"
- Удаление тел запросов, содержащих чувствительные данные
```

#### Шифрование в хранилище

**Elasticsearch шифрование:**
- X-Pack encryption at rest (если доступно)
- Или использование encrypted volumes на уровне ОС

**Transport encryption:**
- TLS для всех соединений между компонентами
- mTLS для внутренних сервисных соединений

### Контроль доступа

#### Кто имеет доступ к логам

| Роль | Доступ | Системы | Ограничения |
|------|--------|--------|------------|
| **Разработчик** | Полный доступ | Все | В рабочее время через VPN, автообновление доступа каждый день |
| **DevOps инженер** | Полный доступ | Все | Все время, требуется аутентификация |
| **QA инженер** | Ограниченный | Все системы | Только DEBUG и выше логи, без доступа к личным данным |
| **Тимлид** | Полный доступ | Все | Все время для быстрого реагирования |
| **Поддержка** | Ограниченный | CRM, Shop | ERROR и WARN логи, с маской личных данных, только поиск по order_id |
| **Продакт-менеджер** | Очень ограниченный | - | Только дашборды с метриками (количество ошибок, время обработки) |
| **Внешний партнер (API)** | Очень ограниченный | API logs | Только свои API ключи, доступ через отдельный Kibana space |

#### Механизм управления доступом

**Kibana RBAC (Role-Based Access Control):**
```
Роль: support_read_only
- Индексы: crm-logs-*, shop-logs-*
- Поля: order_id, timestamp, severity, message (без customer_id, price)
- Операции: search, view, не могут экспортировать

Роль: developer_full
- Индексы: *
- Поля: все
- Операции: search, view, export, delete

Роль: business_dashboard
- Индексы: metrics-*
- Поля: только метрики (count, duration, error_rate)
- Операции: view, не может искать
```

**Аудит доступа:**
- Все запросы к Elasticsearch логируются
- Экспорт/скачивание логов требует апруверования тимлида
- Каждый месяц отчет о доступах

### Retention и соответствие требованиям

**GDPR/CCPA соответствие:**
- Логи содержат только минимум персональных данных (маскировано)
- Автоматическое удаление логов через 90 дней
- Возможность удалить логи по customer_id по запросу

## Политика хранения логов

### Структура индексов

**Elasticsearch индексы по системам:**

```
Index Name Pattern:     shop-logs-yyyy.mm.dd
Lifecycle:
  - Hot (0-7 дней):    в памяти, fast retrieval
  - Warm (7-30 дней):  на диске, slow retrieval
  - Cold (30-90 дней): archived, очень медленный поиск
  - Delete (90+ дней): удаление

Shard configuration:
  - Shards: 3 (распределение нагрузки)
  - Replicas: 2 (надежность)
  - Refresh interval: 30s (баланс между свежестью и производительностью)
```

**Индексы по системам:**

| Индекс | Объем в день | Хранение | Размер в год | Причина размера |
|--------|-------------|----------|-------------|-----------------|

| **crm-logs** | ~1 GB | 90 дней | ~90 GB | Логи бизнес-операций, меньше трафика |

### Расчет требуемых ресурсов

**Elasticsearch кластер:**

```
Indexing rate: 7.5 GB/день = ~87 MB/сек
Typical Elasticsearch: 1 GB per shard per second indexing
Требуется: ~1 shard для indexing

Search требования:
- Операторы ищут по order_id (очень быстро)
- Разработчики ищут по correlation_id (медленнее)
- Аналитика ищет по patterns (очень медленно)

Рекомендуемая конфигурация:
- 3 Data nodes: 8 CPU, 32 GB RAM, 300 GB SSD каждый = 900 GB storage
- 3 Master nodes: 2 CPU, 8 GB RAM каждый
- 2 Coordinating nodes: 4 CPU, 16 GB RAM каждый

Итого: ~1.8 TB storage на горячих данных
Архив: ~2 TB на холодных данных (S3)
```

```yaml
  И это было 5 минут подряд
```

### Поиск аномалий

#### Встроенные правила аномалий в Kibana/Elasticsearch

**Аномалия 1: Внезапный скачок заказов**

```
Метрика: Количество ORDER_INITIATED за 1 минуту
Норма: ~100 заказов/минуту (±10%)
Аномалия: Скачок до 1000 заказов/минуту

Возможные причины:
1. Хакерская атака / DDoS
2. Маркетинговая акция (но должна быть спланирована)
3. Сбой API (клиент повторяет запросы)

Действие: Автоматически включить rate limiting для новых IP
```

**Аномалия 2: Изменение времени обработки**

```
Метрика: P95 время обработки заказа
Исторические данные: 5-7 минут
Аномалия: Скачок до 20 минут

Корреляция с:
- Размером модели (полигоны)?
- Нагрузкой на MES (CPU)?
- Размером очереди RabbitMQ?

Система предлагает вероятные причины на дашборде
```

**Аномалия 3: Паттерн отказов**

```
Событие: Расчет цены падает для моделей 3D studio MAX формата
Обнаружение:
1. Ошибка PRICE_CALCULATION с message содержит "*.max"
2. Статистика: 90% моделей MAX падают, 5% других

Действие:
- Создать тикет для разработчика C#
- Дать рекомендацию клиентам конвертировать в STL
```

**Аномалия 4: Поведение операторов**

```
Метрика: Какой оператор сколько заказов взял в работу
Норма: Более-менее равномерное распределение
Аномалия: Один оператор берет 90% заказов, другие 10%

Возможные причины:
1. Один оператор работает быстрее (может ему увеличить зарплату?)
2. Задача распределяется неправильно в системе (баг)

Доступно через Kibana дашборд для менеджера
```

### Дашборды и визуализация

#### Дашборд 1: "Здоровье системы" (для DevOps)

```
Компоненты:
- Статус компонентов (Green/Yellow/Red)
- Средний response time по системам
- Процент ошибок
- Размер очередей RabbitMQ
- Свободное место на дисках Elasticsearch
- Коннекты к БД
```

#### Дашборд 2: "Полная жизнь заказа" (для бизнеса)

```
Компоненты:
- Количество заказов (Today vs Yesterday vs Average)
- Средний путь заказа (создание → доставка)
- Где застревают заказы (какой статус)?
- Процент успешных заказов
- Время от создания до отправки (распределение)
- API клиенты - количество запросов, процент ошибок
```

#### Дашборд 3: "Логирование и трейсинг" (для разработчиков)

```
Компоненты:
- Самые частые ошибки за день
- Самые медленные операции
- Трейсы с ошибками (можно кликнуть)
- Логи с аномалиями (выделены красным)
- График объема логов (если раптом упало - есть проблема)
```
